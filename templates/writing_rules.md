# SCIWriter 证据优先级与写作规则

## 一、文档目的

本规则用于规范 SCIWriter 在自动读取生信分析结果并生成 SCI 写作内容时的证据使用顺序、事实判定原则和写作约束，确保生成内容尽可能符合真实分析结果，避免因代码版本滞后、文件混乱或大模型自由发挥而导致写作内容失真。

本规则适用于以下内容生成场景：

- Results
- Methods
- Figure legends
- Abstract
- Discussion（部分受限适用）

---

## 二、核心原则

SCIWriter 的总体原则为：

**最终写作以结果表和最终图为主证据，代码只作为方法辅助信息来源，不能凌驾于最终结果之上。**

换言之：

- 结果事实以最终结果文件为准
- 图像用于辅助验证和结果呈现判断
- 代码用于辅助解释分析方法
- 如果代码与结果不一致，优先相信最终结果，并采用保守写法

---

## 三、证据优先级总则

### 1. Results 章节证据优先级

Results 的事实性内容必须按照以下优先级确定：

#### 一级证据（最高优先级）
- `evidence.csv`
- 最终结果表
- 经程序提取后的结构化结果文件
- 已确认的关键统计结果文件

例如：
- `diffSig.xls`
- `uniCox.txt`
- `lasso_features.csv`
- `GSEA_result.xls`

#### 二级证据
- 最终图片
- 图像对应的文件名、图类型、图序号
- 图注草稿（如后续存在）

例如：
- `volcano.png`
- `heatmap.png`
- `forest.png`
- `KM.png`
- `ROC.png`

#### 三级证据
- 项目级和模块级结构化说明文件

例如：
- `project.yaml`
- `storyline.md`
- `module_context.json`

#### 四级证据（最低优先级）
- 代码文件
- 历史脚本
- 中间处理脚本

例如：
- `.R`
- `.py`
- `.sh`

### 2. Methods 章节证据优先级

Methods 的信息来源与 Results 不完全相同，但同样不能单纯以代码为准。

Methods 应按以下优先级进行综合判断：

#### 一级证据
- 最终结果表能够确认的分析类型
- 最终图能够确认的分析展示形式
- 模块类型识别结果

#### 二级证据
- 代码文件
- 软件包名
- 函数调用
- 阈值和参数

#### 三级证据
- 文件夹名
- 文件命名方式
- 项目路线模板
- 保守模板推断

### 3. Figure legends 证据优先级

图注生成应优先参考：

1. 图片文件本身
2. 对应模块的 `evidence.csv`
3. 对应模块的 `module_context.json`
4. 必要时参考结果表
5. 最后才参考代码

---

## 四、不同章节的证据使用规则

## 1. Results 章节规则

Results 章节必须严格遵守以下规则：

### 规则 1：所有数值以最终结果表或结构化 evidence 为准
包括但不限于：

- 基因数
- 上调/下调数
- HR
- p 值
- AUC
- 富集条目数
- 风险基因数
- 保护基因数

如果这些信息没有在结果表或 `evidence.csv` 中明确出现，则不得自行写出。

### 规则 2：代码不得决定 Results 中的事实内容
代码只能辅助判断“这一步可能做了什么分析”，不能直接作为结果事实来源。

例如：
- 代码里出现 edgeR，不代表最终结果一定来自 edgeR 当前版本
- 代码里阈值写成 `FDR < 0.05`，不代表最终导出的结果表一定沿用了这个阈值
- 如果代码和结果表不一致，Results 必须以结果表为准

### 规则 3：图用于辅助判断趋势，不用于替代精确数值
例如：
- 可以通过火山图判断存在明显上调和下调基因
- 可以通过森林图判断存在风险和保护方向
- 但具体数量、HR、p 值必须来自结果表或 evidence 文件

### 规则 4：没有 evidence 支持时，宁可少写，也不能补写
如果 `evidence.csv` 中没有：
- 具体 HR
- 具体 p 值
- 具体代表基因统计值

则 Results 中不得自行补充这些数字。

### 规则 5：Results 语言以“描述事实”为主，不做过度推断
应避免：
- 机制化表达
- 因果化表达
- 夸大性表达

---

## 2. Methods 章节规则

Methods 章节遵循“结果确认分析类型，代码补充实现细节”的原则。

### 规则 1：先确认分析类型，再补方法细节
Methods 写作时，优先根据：
- 结果表
- 图片类型
- 模块识别结果

确认该模块属于哪类分析，再结合代码补充软件包和具体方法。

### 规则 2：代码可以提供方法线索，但不能无条件照搬
如果代码与结果存在以下问题：

- 代码版本明显滞后
- 同目录存在多个脚本版本
- 代码与结果表字段不匹配
- 图表显示内容与脚本逻辑不一致

则 Methods 应降级写成更保守版本，而不要硬写具体包名和参数。

### 规则 3：Methods 可以采用三种模式生成

#### 模式 A：代码驱动
适用条件：
- 有明确代码文件
- 代码内容与结果表和图一致
- 软件包和方法可明确识别

写作粒度：
- 可以写具体方法名
- 可以写软件包名
- 可以写阈值和统计标准

#### 模式 B：结果驱动
适用条件：
- 没有可靠代码
- 但有清晰结果表和图

写作粒度：
- 可写分析类型
- 可写基本统计框架
- 不写不确定的软件包和细节参数

#### 模式 C：结构保底
适用条件：
- 没有代码
- 结果信息有限
- 只能根据模块结构识别分析类型

写作粒度：
- 仅写保守版 Methods 描述
- 避免具体实现细节

### 规则 4：Methods 宁可保守，不可假精确
如果系统无法确认：
- 软件包
- 参数阈值
- 统计检验细节

则不要硬写，只写：
- “Differential expression analysis was performed...”
- “Univariate Cox regression analysis was conducted...”

而不要虚构更具体的实现过程。

---

## 3. Discussion 章节规则

Discussion 不直接以代码或单一结果文件为事实依据，而应基于：

1. 已确认的 Results 内容
2. 文章主线
3. 模块之间的逻辑关系
4. 保守学术解释

### 规则 1：Discussion 不能引入 Results 中未确认的数字
### 规则 2：Discussion 可以做解释，但不能越过证据边界
### 规则 3：Discussion 不得把相关性结果直接写成机制结论

---

## 五、代码与结果冲突时的处理原则

当代码与结果表、图片出现不一致时，应按以下原则处理：

### 情况 1：结果表明确，代码不明确
处理方式：
- 以结果表为准
- 代码仅作为辅助，不写具体实现细节

### 情况 2：图片与结果表一致，但代码不同
处理方式：
- 以结果表和图片为准
- Methods 写保守版本
- Results 不参考代码中的冲突细节

### 情况 3：代码、图、表三者明显冲突
处理方式：
- 优先保留最终结果表
- 图像作为辅助参考
- 代码降级为低优先级
- 输出中使用保守表述
- 必要时标记该模块为低置信度

---

## 六、建议增加的证据置信度机制

为了提高系统稳健性，建议后续为每个模块增加置信度字段。

例如：

- `high`：结果表、图片、代码高度一致
- `medium`：结果表和图片可支持，代码不完整或不稳定
- `low`：仅能从结构和少量文件推断

可参考字段：

```json
{
  "final_fact_source": "result_table",
  "code_support": "medium",
  "figure_support": "high",
  "confidence": "high"
}
```

或者：

```json
{
  "preferred_result_source": "uniCox.txt",
  "preferred_method_source": "Autophagy.uniCox.R",
  "code_matches_results": false
}
```
## 七、写作约束规则

以下规则适用于所有自动生成内容。

### 1. 不编造规则

若结构化证据中未明确给出以下内容，则不得自动补写：

- 数值
- 统计结果
- 方法细节

### 2. 保守表达规则

优先使用以下表达：

- `was associated with`
- `was identified`
- `was observed`
- `was retained`
- `suggested`

避免使用以下表达：

- `drove`
- `caused`
- `mediated`
- `induced`
- `confirmed mechanism`

### 3. 证据一致性规则

生成内容必须与以下文件保持一致：

- `evidence.csv`
- `project.yaml`
- `storyline.md`
- `module_context.json`

### 4. 模块顺序规则

章节组织必须优先遵守以下字段：

- `results_order`
- `main_text_modules`

不得由模型自由改变主要模块顺序。

---

## 八、总结

SCIWriter 的证据使用必须遵守以下总原则：

### Results

结果表和最终图优先，代码不能覆盖最终结果。

### Methods

结果确认分析类型，代码补充实现细节；若代码与结果不一致，则采用保守写法。

### 整体

优先使用最终结果证据，避免模型根据旧代码或不完整脚本过度推断。

该规则应作为 SCIWriter 后续所有模块开发、模板设计和写作生成的统一约束基础。
